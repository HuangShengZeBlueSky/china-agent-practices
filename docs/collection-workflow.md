# 从广泛收集到可迁移学习

这份工作流用于持续维护本仓的研究资料、方法卡和看板。采集阶段让材料可追溯，阅读阶段解释实现，实践阶段才判断一种方法是否适合自己的任务。当前仓库完成前两部分，没有配置定时采集或运行上游 Agent。

## 1. 先建立来源地图

以公司和具体工程问题共同确定检索范围。公司的覆盖让我们看见不同团队，工程问题的覆盖让材料有可比较之处。例如同样研究技能，飞书适合看业务流程与 CLI 契约，Eino 适合看加载通道，AgentScope 适合看能力启用，腾讯 RTC 适合看会话状态，MiniMax 适合看任务阶段与产物要求。具体依据见 [方法地图](method-map.md) 与 [结构化方法卡](../catalog/methods.json)。

优先顺序为官网关联的仓库、官方组织的具体实现、官方产品文档、单独标记的第三方归档。产品名出现在路径里只能证明路径这样命名；官方平台收录一个插件，也不能自动证明插件由该公司原创。每项正式记录保留 `ownership_evidence`（归属依据）。

这一轮按公开工程材料扩展至 15 个公司或研究机构，模型公司与研究机构明确标记为扩展对照。还没有找到可核查实现的线索不进入“源码已核对”统计。

## 2. 盘点原文，固定快照

先记录仓库地址、提交、分支、检查日和许可，再读取目录树。大仓库必须检查树结果是否截断，必要时按子树分段读取。统计只使用明确口径：

| 对象 | 本仓怎样统计 | 不能直接推断什么 |
| --- | --- | --- |
| 组织 | 官方来源对应的公司或研究机构去重 | 组织数不是互联网大厂数量 |
| 仓库 | GitHub owner / repository 去重 | 同一仓库多个专题不是多个仓库 |
| 研究条目 | 有明确问题、已读材料与边界的记录 | 一条记录可能对应多份文件 |
| 已核对材料 | `inspected_files` 中具体 URL 去重 | 不保证穷尽大型文件所有分支 |
| 技能路径 | 文件名严格为 `SKILL.md` 的路径 | 不等于独立技能、原创技能或正在启用的技能 |
| 内容去重 | Git blob 标识相同的内容合并 | 不等于语义相同或功能相同 |

归档目录统计的完整定义保存在 [archive-research.json](../catalog/archive-research.json)。2,792 个路径只保存路径、提交、blob 与状态等元数据；代表性正文另行深读。作者 README 的 1,199 个条目使用另一口径，两个数字不能相减解释成“漏收了多少技能”。

## 3. 选择能解释机制的文件

每个项目优先读一条完整路径：入口如何接受任务，模型请求由哪些消息组成，工具怎样注册和执行，返回如何写回，错误如何表示，以及循环为什么结束。对应文件可能是系统提示、技能入口、参考资料、参数 schema、执行器、状态工具或评估器。

读 Skill 时至少同时看入口、它引用的关键参考和依赖工具。读 CLI 时同时看命令说明与返回协议。读 Agent 框架时同时看提示构造器和调用者。读评估时区分格式检查、字符串匹配、模型评分和真实任务验收。单独读一段提示词不足以回答它在何时生效。

只通过目录树知道存在的文件，写 `tree_presence_only`（只确认路径存在），不放入正文已读数量。大型索引只检查概览和结构时写清 `coverage` 或 `reading_scope`，不称为逐项理解。

## 4. 用模型完成语义阅读和方法提炼

程序适合比较哈希、验证链接结构、生成索引和检查字段。用途分类、协议理解、证据冲突、方法迁移需要阅读正文后的判断。本仓的语义标签和方法卡由研究者整理，生成脚本不根据关键词猜测技术机制。看板的搜索只对这些已有记录作字面匹配。

归档作者的采集脚本采用现有元数据、目录前缀和关键词规则组织导航；根 README 的近期总结则由模型另行整理。这两者的职责和限制已在 [归档方法拆解](../cases/archive-collection-method.md) 中说明。我们借鉴其版本与变更记录方式，再增加来源分级、调用链解释与迁移练习。

一张可用的方法卡应当回答六件事：

| 字段 | 应写的内容 |
| --- | --- |
| 问题 | 哪种具体失败或维护成本促成了这项设计 |
| 机制 | 哪些文件或函数实际做了什么 |
| 证据 | 固定提交、路径和阅读范围 |
| 适用条件 | 宿主、权限、状态与工具方面有什么前提 |
| 迁移练习 | 在自己的项目上改什么、观察什么 |
| 边界 | 哪些效果没运行验证，哪些只在提示文本中出现 |

方法卡保存于 [methods.json](../catalog/methods.json)，路线保存于 [learning-paths.json](../catalog/learning-paths.json)。这两份文件里的 `source_ids`（来源标识）必须指向真实来源记录，生成看板时会校验。

## 5. 从来源变化更新结论

发现新的提交后，优先比较已经作为证据的文件和它们的调用者。记录“变化是什么、旧结论还能否成立、哪些问题需要重读”。保留旧提交引用作为历史依据，修订当前说明时在 CHANGELOG 中解释原因。

不要用版本号大小推断渠道间的先后关系。飞书官方与豆包归档 Base 的版本、职责并不相同；openJiuwen 同一快照的文档和代码也有具体接口差异。归档 QwenWork 的 QA 文件与链路协议出现路径和标记差异。正确的更新结果可以是“存在冲突，尚未运行验证”，不必把它们强行整理成一个一致实现。

像 AgentScope Runtime、Kimi CLI Python 版这样的迁移或归档信息，作为 `lifecycle_note`（维护状态说明）直接显示在看板卡片上。历史实现仍能帮助学习，但不当作当前安装入口推荐。

## 6. 同步仓库与看板

正式内容集中在以下位置：

| 文件 | 内容 |
| --- | --- |
| `catalog/sources.json` | 35 条已审阅研究来源、组织、固定版本、方法与边界 |
| `catalog/methods.json` | 跨项目工程方法 |
| `catalog/learning-paths.json` | 按目标排列的学习步骤与交付物 |
| `catalog/archive-research.json` | 归档作者方法、统计、代表样本与差异 |
| `catalog/archive-skill-index.json` | 完整技能路径元数据，保留 blob 与历史状态 |
| `catalog/archive-inventory.json` | 供网页使用的归档展示数据与简化索引 |
| `cases/` | 原创中文实现拆解 |
| `dashboard/` | 可直接托管的静态看板 |

修改数据和研究文档后，在仓库根目录执行：

```bash
python3 scripts/build_dashboard.py
```

脚本会检查来源标识、分类、提交格式、案例存在性和方法引用，重建 `catalog/README.md` 与 `dashboard/data.js`。不需要调用模型、联网或安装上游项目。网页渲染器 Marked 已随仓库提供，保留其 MIT 许可。

网页源代码和研究数据一起版本管理。原始材料仍留在上游，本仓保存自己的分析和链接；第三方归档没有明确根许可，完整路径索引不含技能正文。

## 7. 将“学到”落到一次实验

先选择一个具体问题和一个可检查产物，例如“长工具输出压缩后仍能判断失败原因”，或“超时后续查任务不会重复创建”。固定模型、工具版本、输入和环境，记录模型实际看到的消息、工具调用、执行结果和验收结果。

一次只改变与问题相关的变量，先得到可以解释的结果再考虑扩大实验。没有实跑的数据保持 `execution_status: not_run`。看板中用户自行设置的“已读／已实践”是个人学习进度，不会自动改写研究证据等级。

本轮完成的是来源扩展、静态拆解、方法汇总和浏览入口。后续实验需要单独留下轨迹与产物，才进入“已复现”的范围。
