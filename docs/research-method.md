# 怎样拆出可复用的方法

本仓库的基本单位是“一个有证据的工程做法”。公司和项目负责导航，真正要积累的是：某个问题怎样被发现，系统增加了什么约束或能力，输入输出发生了什么变化，以及这种做法在哪些条件下有用。

## 六类材料分别回答什么

| 材料 | 要回答的问题 | 值得保存的证据 |
| --- | --- | --- |
| Prompt，提示词 | 模型此刻被要求做什么，如何定义完成，如何表达失败？ | 模板正文、模板变量、拼装函数、运行时条件 |
| Skill，技能包 | 什么时候选它，先读什么，后读什么，怎样知道做对了？ | SKILL.md、参考文档、辅助脚本、元数据与加载实现 |
| CLI，命令行工具 | 模型怎样探索可用操作、传参、接收结果、处理错误？ | 帮助、参数模式、返回结构、退出码、预演与授权流程 |
| Tool / API，工具与程序接口 | 一个动作的输入、权限、副作用和输出是什么？ | 接口定义、执行器、权限边界、异常和恢复分支 |
| Harness，智能体运行脚手架 | 谁安排循环、上下文、工具与状态，何时暂停或结束？ | 模型调用处、消息列表、调度器、状态与轨迹格式 |
| Evaluation，评价与反馈 | 怎样判断完成、发现回归、保留经验？ | 断言、环境状态检查、评测器、审查规则、变更记录 |

一个项目通常覆盖多类材料。例如命令行只是执行入口，背后不一定调用语言模型；一个 Markdown 技能包可能包含丰富的工作方法，但是否被加载、何时加载，需要运行代码或产品文档进一步证明。

## 来源类型与验证深度是两条轴

| 来源类型 | 可以据此说什么 | 不能直接据此说什么 |
| --- | --- | --- |
| 官方源码 | 该公开快照包含某段实现 | 闭源线上产品一定运行同一版本 |
| 官方产品文档 | 官方对用户承诺了某种能力或配置方式 | 后台完整提示词、调度、算法细节已经公开 |
| 官方技术文章、论文 | 作者报告了某种设计或实验结果 | 我们已复现其效果，或产品所有业务都用它 |
| 第三方归档 | 某份可见文件含有这些内容，归档者作了某种声明 | 内容得到厂商授权，属于当前生产版本，或完整无删改 |
| 社区实现 | 该社区项目提供某种功能 | 同名大厂产品的内部实现就是它 |

验证深度另记为“已读正文”“源码静态核对”“已运行最小示例”或“已复现任务”。首版主要是前两类。公开链接能打开和执行链能跑通是不同事实。材料真实可读，也不代表方法一定有效；效果需要另外设计实验。

## 先追调用链，再解释提示词

看到系统提示词后，先找负责组装它的函数，再找实际发起模型请求的位置。记录用户输入、系统指令、项目说明、已选技能、检索资料、工具模式和历史消息之间的关系。分别标明谁执行检索、结果插入哪种消息；不能仅凭资料进入了系统消息，就假定模型拥有一个可自行调用的检索工具。如果技能正文来自一次工具调用，也不要写成一开始已经放进系统提示词。

同样要追工具返回后的路径：结果以什么角色或事件回到模型，输出过长时怎样处理，错误能否重试，部分成功是否被保留，模型什么时候继续思考、什么时候停止。如果有 SDK（软件开发包）把请求转交云端，公开代码只能证明客户端这一段，云端提示词需要明确记为不可见。

## 每个案例保留七个答案

1. **问题与适用范围：** 解决的具体失败是什么，在哪类任务里出现？
2. **最小原料：** 用户任务、文件、状态、权限、工具等分别来自哪里？
3. **调用前上下文：** 模型实际能看到哪些内容，哪些仍在外部文件或服务中？
4. **执行顺序：** 哪部分由模型决定，哪部分由普通程序执行？
5. **完成与失败：** 成功由什么证据确定，错误如何返回与恢复？
6. **迁移建议：** 可以借哪一小块，依赖和代价是什么？
7. **证据边界：** 已读哪些文件，固定在哪个版本，哪些没有验证？

第六项是我们自己的判断，要和前五项的来源事实分开。不要用“行业最佳实践”“大厂都这么做”代替适用条件。

## 研究入口和收录门槛

从官网、官方开发者站、GitHub 官方组织开始，先确认归属，再检索 SKILL.md（技能说明）、AGENTS.md（仓库工作约定）、prompt（提示词）、tool（工具）、schema（参数结构）、middleware（处理中间层）、context（上下文）、trajectory（执行轨迹）等实现入口。文本搜索负责定位文件，语义解释和研究判断由模型阅读完成。

正式案例至少需要一份能够支撑关键结论的具体材料，不能只引用首页宣传语。发现有趣项目但暂时读不到实现，就进入待研究清单；记录“未找到”时，只说明本轮检查范围，不断言整个互联网不存在。排名、星标和热度只作为线索，不作为方法质量指标。

## 更新方式

后续更新先挑一个明确问题，例如“飞书如何让 Agent 从错误里知道下一步”，围绕该问题检查已有来源是否变化，再新增必要证据。代码有变化时比较与结论有关的文件，保留原先固定提交。只有结论改变才更新案例解释，顺手同步来源目录和变更记录。

原始文件、调研笔记、可迁移建议分别承担不同职责：原文用链接保真，案例用中文解释，方法对照表帮助横向查找。这样的分工便于学习，也便于将来让另一个 Agent 接续研究。
